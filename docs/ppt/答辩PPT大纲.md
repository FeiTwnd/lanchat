## 第 5 页 总体架构

- 幻灯片标题：C/S 分层架构
- 部署形态：一服务器多客户端，TCP 承载消息与文件，UDP 承载发现
- 三层代码结构：界面层 / 网络与业务层 / 数据与工具层
- 公共模块双端共享：消息模型、枚举、实体、配置、异常、工具
- 依赖方向单向：界面依赖网络门面，业务依赖 DAO 接口，无反向依赖

要点（3 至 5 条）

1. 部署两层、代码三层，公共模块是双端一致性的根本保障。
2. 界面层只认识 ChatClient 一个网络门面，界面代码零 Socket。
3. 业务层只依赖 DAO 接口，因此可以在测试中注入独立测试库的数据源，业务代码不感知连接串。
4. 依赖单向，不存在循环依赖。

配图：《04-实现说明》图 4-1 项目分层与依赖关系（或报告图 3-1）。

讲解要点与时长：60 秒。用一句话讲清「为什么公共模块共享能消灭一整类协议不一致问题」。

## 第 7 页 消息模型与多态

- 幻灯片标题：协议即模型：Message 继承体系
- Message 抽象基类：id、type、sender、receiver、timestamp，抽象方法 getSummary
- 三个子类：TextMessage、FileMessage、SystemMessage

要点（3 至 5 条）

3. 编号由 AtomicLong 保证跨线程唯一。
4. 枚举反查对未知名称回退为 SYSTEM，保证读旧记录不中断。

## 第 9 页 线程与网络通信模型

- 幻灯片标题：多线程模型与共享资源
- 服务器：accept 线程、连接线程池（按需创建、上限 200、空闲 60 秒回收）、心跳扫描定时线程、UDP 应答线程
- 客户端：接收线程、发送线程池、心跳调度器、文件发送线程
- 三类共享资源的三种并发工具：发送锁、ConcurrentHashMap、CopyOnWriteArrayList
- 界面更新一律调度到 Swing EDT

要点（3 至 5 条）

1. 区分「必须串行化」与「可并发」的资源，而不是一律加锁。
2. 同一对象输出流由发送锁保护，防止字节交错。
3. 在线表用 putIfAbsent 语义保证同名账号并发登录只有一个成功。
4. 网络线程绝不直接操作 Swing 组件。

配图：报告图 3-7 线程模型图（或《04-实现说明》图 4-3 时序图）。

讲解要点与时长：70 秒。这是答辩高频追问区，务必能清楚说出「为什么输出流必须串行化」。

## 第 10 页 通信协议设计

- 幻灯片标题：协议：34 种消息类型与三条规则
- 类型集中：全部使用 MessageType 枚举，序列化天然一致
- 文本承载：USER_LIST 与 FILE_REQUEST 用编解码器处理，制表符分隔加转义
- 形态一致：服务器转发原始消息对象，不重新构造
- 方向语义：sender 与 receiver 的方向在两端含义相反，回执必须显式构造
- 边界校验：控制报文字段数上限 16、拒绝控制字符；反序列化白名单只放行四个包并限制四项资源上限
- 可靠投递类型：MSG_ACK 送达确认、OFFLINE_MESSAGE 离线补投、SESSION_RESUME 会话恢复均已接入；EXPORT_REQUEST/EXPORT_RESULT 支撑服务端查库导出

要点（3 至 5 条）

1. 协议权威定义就是共享的类与枚举，双端只有一份。
2. 为什么两处仍用文本承载：服务器需要先校验再转发，且文本便于日志排查。
3. 「转发原始对象」这条规则直接来自一次 ClassCastException 缺陷。

配图：报告表 3-3 协议消息类型与方向表。

讲解要点与时长：50 秒。讲清楚「对象序列化在两端同版本时是最高效的协议」，并主动说出它的代价：无版本协商。

## 第 11 页 关键技术难点一：对象流的两个陷阱

- 幻灯片标题：对象流死锁与内存泄漏
- 陷阱一：ObjectInputStream 构造时阻塞读取对端头部，两端都先构造输入流会互相等待形成死锁
- 解法：先构造 ObjectOutputStream 并立即 flush，再构造 ObjectInputStream
- 陷阱二：ObjectOutputStream 缓存已发送对象以复用引用，长时间运行造成内存持续增长
- 解法：每次 writeObject 后 flush 并 reset，牺牲少量带宽换内存稳定
- 并发写入：心跳、聊天、文件块来自不同线程，必须由发送锁串行化

要点（3 至 5 条）

1. 这两个陷阱都不是「写错了」，而是流对象本身的语义决定的，必须理解原理才能避免。
2. reset 的代价与收益要能说清楚：重复发送同一对象时体积略增，但内存不再增长。
3. 发送锁的粒度是「整个对象写入」，不能细分。

配图：报告图 3-7 线程模型图中发送锁与接收线程的标注截图，或《04-实现说明》5.7 节读取循环伪代码的截图。

讲解要点与时长：80 秒。这是本答辩最有含金量的一页，建议配合一段两行代码的口头描述（先 out 后 in、写完 reset）。

## 第 12 页 关键技术难点二：身份不可伪造

- 幻灯片标题：服务器强制覆盖发送者
- 问题：客户端完全可以在消息里把 sender 写成别人的名字
- 方案：服务器从当前连接取出「已登录用户名」，强制覆盖消息的 sender 字段，然后才进入分派
- 配套：未登录连接除注册与登录外的消息一律拒绝；凭据字段不随用户对象传输（clearCredential 脱敏）
- 效果：客户端无法冒充他人，接收方看到的发送者一定是真实登录身份

要点（3 至 5 条）

1. 安全设计的第一原则是「不信任客户端输入」，哪怕是消息体里的字段。
2. 身份的唯一来源是连接状态，而不是消息内容。
3. 同时做了两件事：防伪造与凭据脱敏。

配图：报告图 4-2 文件传输时序图（如需展示发送者覆盖环节，可改用《04-实现说明》图 4-5 私聊路由流程图并高亮「强制覆盖 sender」节点）。

讲解要点与时长：50 秒。可以现场提问式讲解：「如果不做这一步，会发生什么？」

## 第 13 页 关键技术难点三：文件完整性

- 幻灯片标题：文件传输的完整性与失败清理
- 分块：64KB 一块，发送侧用 RandomAccessFile 按块随机读取，内存占用与文件大小无关
- 校验：块序号必须严格连续，全部收完后流式计算 SHA-256 并与发送方声明的比对
- 清理：校验失败、块乱序、用户取消三种情况都必须删除残缺文件
- 上限：单文件 200MB，在发送方本地即拒绝，不产生网络流量
- 服务器只中继不落盘，避免成为磁盘与带宽瓶颈
- 发起入口在聊天窗口内：私聊窗口固定发给对端；群聊窗口先把文件群发给全部在线用户，即对每人各发起一次独立传输，各自确认、互不影响

要点（3 至 5 条）

1. 残缺文件比失败提示更危险，因为它「看起来正常但内容损坏」。
2. 清理逻辑必须同时覆盖 IO 异常与业务异常——这正是修复过的缺陷之一。
3. 服务器零存储是刻意的架构取舍，代价是无法断点续传。

配图：《04-实现说明》图 4-7 文件分块发送与校验时序图，或《04-实现说明》图 4-8 文件接收状态流转图。

讲解要点与时长：70 秒。重点讲「三种失败路径都清理」与「服务器零存储的取舍」。

## 第 14 页 局域网自动发现

- 幻灯片标题：UDP 广播实现零配置发现
- 客户端枚举本机全部网卡的广播地址，逐个发送探测报文，而不是简单用 255.255.255.255
- 服务器应答自身 IP、TCP 端口与当前在线人数
- 服务端加固：报文长度与格式严格校验，单来源限流 5 次/秒（突发 10），畸形包静默丢弃且不影响监听线程
- 超时窗口内持续收集应答，按 IP 加端口去重
- 降级路径：发现失败可手工输入 IP，回环地址显式识别便于单机自测

要点（3 至 5 条）

1. 多网卡与虚拟网卡环境下，按子网掩码计算各自的广播地址才能保证发现成功率。
2. 去重是必要的：同一服务器可能从多张网卡各应答一次。
3. 任何自动发现都必须有手工降级路径，因为企业网络常屏蔽广播。
4. 面向无连接的 UDP，服务端必须自带格式校验与来源限流，否则一个伪造包就能放大成资源消耗。

配图：《04-实现说明》图 4-10 UDP 自动发现时序图，以及报告图 B-2 真实发现结果截图。

讲解要点与时长：60 秒。主动说明局限：受限于广播域，且依赖 UDP，因此必须有降级。

## 第 15 页 数据持久化设计

- 幻灯片标题：MySQL 唯一存储：三张表与正文加密
- 存储收敛：用户、聊天记录、文件传输日志分别落 chat_user / chat_message / chat_file_log，启动时自动建表
- 用户表：username 为主键，salt 与 password_hash 分开存储，另有角色与登录时间
- 聊天记录表：message_id 稳定标识加唯一索引，delivered 支持离线补投；read_flag 与 recalled 为撤回与已读回执预留
- 正文加密：content 列写入前经 AES-GCM 加密并带 enc:v1: 前缀，直接查库只能看到密文；加密口令缺失时服务器拒绝启动
- SQL 全部走 PreparedStatement 占位符，杜绝字符串拼接注入
- 磁盘只保留两类产物：data/received 接收文件与 data/export 导出记录；导出由服务端查库渲染后回传客户端落盘
- 时区陷阱：db.url 的 serverTimezone 必须填数据库所在机器的真实时区，否则命令行直接查库会差若干小时

要点（3 至 5 条）

1. 关系表把时间范围查询交给索引，不再需要手工解析文件。
2. 加密与建表都收口在数据访问层，业务层只依赖 DAO 接口。

## 第 16 页 密码安全设计

- 幻灯片标题：口令 PBKDF2 与正文 AES-GCM
- 口令散列：PBKDF2WithHmacSHA256、12 万次迭代、格式 pbkdf2$120000$hex，随机 16 字节盐
- 兼容历史：升级前的单轮加盐 SHA-256 仍可登录，登录成功后透明重算为 PBKDF2，用户无需改密
- 校验方式：常量时间比较，抵御时序侧信道；凭据不随用户对象经网络传输，对外返回的用户对象统一脱敏
- 正文落盘加密：AES-GCM、enc:v1: 前缀，密钥由 security.message.secret 经 PBKDF2 派生，固定盐保证重启后可解密
- 安全默认值：加密口令缺失时服务器直接拒绝启动，不提供任何内置默认密钥；口令变更后历史密文无法解密
- 诚实边界：以上只保护落盘正文，网络传输仍是 Java 原生序列化的明文 TCP 报文，局域网内抓包可见
- 测试保障：断言存储中存在盐与散列、断言对外对象不含凭据

要点（3 至 5 条）

1. 为什么不用 MD5：抗碰撞性不足，且不加盐无法抵御彩虹表。
2. 为什么用 PBKDF2 而不是单轮 SHA-256：把迭代次数作为人为时间成本写进算法，爆破成本提高数个数量级。
3. 为什么用常量时间比较：普通比较的耗时会泄露前缀匹配长度。
4. 必须主动说出传输层仍是明文，不能把「落盘加密」说成「通信加密」。

配图：报告图 B-9 数据库中 salt 与 password_hash 字段截图。

讲解要点与时长：60 秒。主动说明落盘加密与传输加密的区别，体现对安全边界的诚实。

## 第 20 页 缺陷修复案例（真实工程过程）

- 幻灯片标题：十八个真实缺陷、修复与第一轮安全加固
- D1 存储介质被环境隐式决定：只要 classpath 上存在 MySQL 驱动就自动切换，先改为显式开关，后续进一步收敛为「仅 MySQL 存储」，删除文本文件落盘方式与开关
- D2 工厂类型误用：USER_LIST 调用只接受文本的工厂方法导致连接线程退出，改为先创建再覆写类型
- D3 文件请求强转失败：文本承载元信息却被强转 FileMessage，改为先解码校验再转发原始对象
- D4 回执方向错误：借用了源消息方向字段导致回执投递回自己，改为显式「当前用户到对端」
- D5 校验失败未清理：只捕获 IOException，业务异常绕过删除逻辑
- D6 单例提前初始化：配置未读取就被固化，改为 start 时延迟创建
- D7 集成测试竞态：上线通知早于监听器注册，改为连接时即注册缓冲监听器
- D8 至 D14（系统测试、验收与实机运行阶段）：并发连接上限实际只有 8、同机自动发现失效、两项配置未生效、集成用例竞态、登录后连接被登录窗口关闭、断连提示重复弹窗、数据文件头注释被误报（该缺陷已随文件落盘方式删除而不复存在）
- D15 至 D17（界面走查阶段，由 Xvfb 加 java.awt.Robot 真实窗口走查发现）：接收文件时界面整体死锁、同一条消息渲染两遍、发送私聊后弹出「与自己私聊」的窗口，明细见《测试报告》第九节、现场证据见第十二节
- D18（精简改造阶段，由组件级离屏渲染加像素断言发现）：好友树选中行被系统外观（GTK）的主题橙色渗入，根因是系统外观填充整行背景而自绘渲染器只覆盖图标与文字，改为基础外观加自绘选中色

要点（3 至 5 条）

1. 十八个缺陷全部来自真实开发与测试过程，不是编造的案例。
2. 其中四个是「静默错误」：不崩溃，只是结果不对。
3. 后期高严重程度缺陷的暴露路径各不相同：并发上限只有真实规模才暴露，登录后断连只有经过窗口生命周期才暴露，接收文件死锁只有真实图形环境加线程转储才暴露——说明容量指标、界面资源所有权与 Swing 线程模型都需要单独的验证手段。

# 常见答辩问题与回答准备

以下问题按答辩现场出现频率排序。回答原则：先给结论，再给依据，最后说明取舍；不要背诵，准备成一个可以在三十秒内讲清楚的小故事。

**问题 1：为什么用 Java 对象序列化，而不用 JSON 或自定义二进制协议？**

答：三点理由。第一，本项目双端共用同一套消息类，对象序列化让「协议即类定义」，不需要维护两套编解码代码，也不会有字段名拼写不一致的问题。第二，消息类型用枚举定义，序列化后天然保持类型安全。第三，题目约束是纯 Java SE、不引入第三方库，用 JSON 就需要自己写解析器或引入依赖。它的代价我也清楚：没有版本协商，两端类版本不一致时可能反序列化失败；排查问题时二进制不如文本直观。改进方案是在握手阶段交换协议版本号，不一致时给出明确提示。补充一点：本项目中真正需要文本的地方（在线用户列表、文件请求元信息）我确实用了文本编解码器，原因是可以先校验再转发，也便于日志排查。

**问题 2：TCP 是流式协议，粘包和拆包怎么处理？**

答：使用 Java 原生对象流时，粘包与拆包由 ObjectOutputStream 与 ObjectInputStream 自己处理。对象流在写入时会给每个对象加上头部信息（魔数、版本号、类描述、字段数据与块边界标记），读取端按这个格式解析，因此每次 readObject 拿到的都是一个完整对象，不会出现把两个对象粘在一起的情况。代价是有额外的协议开销——每个对象都有头部，小的消息比自定义长度前缀协议体积更大。如果改成自定义协议，做法是「长度前缀加消息体」：先读固定长度的长度字段，再按长度读满消息体，用一个 ByteBuffer 累积缓冲区循环切割。这也是我理解粘包本质的方式：粘包不是 TCP 的问题，而是应用层没有给出消息边界。

**问题 3：为什么服务器不转发文件内容，而让客户端之间直传或中继？**

答：本项目的实际做法是：客户端把文件分块发给服务器，服务器把消息对象原样转发给接收方，服务器既不缓存文件内容也不落盘。这样服务器的内存占用与磁盘占用与文件大小完全无关，瓶颈只落在网络带宽上，200MB 的文件也不会把服务器磁盘写满。如果服务器落盘，就需要处理临时文件清理、磁盘配额、并发写冲突等一堆问题，对教学规模完全没必要。代价是传输过程依赖发送方持续在线，无法断点续传，我在报告的不足与展望里明确写了这一点。

**问题 4：两个客户端并发登录同一个账号，你的代码怎么保证不会都成功？**

答：在线表是 ConcurrentHashMap，注册时不是「先 containsKey 再 put」，而是用 putIfAbsent 语义：把「检查」和「写入」合并成一个原子操作。返回值不为 null 表示该用户名已经在线，第二个连接就会收到「账号已在别处登录」的拒绝结果。如果先检查再写入，两个线程可能同时通过检查，这就是典型的检查后使用竞态。此外，用户名到连接的映射以用户名为键，天然保证一个用户名只对应一个连接。

**问题 5：心跳 15 秒、超时 60 秒、扫描 20 秒，这三个数字是怎么定的？**

答：思路是「超时时间要能容忍若干次心跳丢失」。15 秒发一次，60 秒无活跃判定掉线，也就是允许连续丢 3 次心跳才判定掉线，避免网络抖动造成的误判。扫描周期 20 秒小于心跳间隔，是为了让判定与清理及时发生；最坏情况下一个掉线连接会在 60 到 80 秒之间被回收。另外这三个值都在 chat.properties 里可配置，部署环境不同可以调整。这三个数字不是拍脑袋，而是「容错次数决定超时、清理频率不超过心跳间隔」这两条规则推出来的。

**问题 6：为什么最终只保留 MySQL 存储，不再提供文件存储？**

答：因为关系表能直接表达这个系统真正需要的三件事：按用户与时间范围的条件查询走索引、稳定消息标识的唯一约束用于幂等去重、以及按传输结果做统计。用文本文件做这些事都要手工解析与全量扫描，越往后越难维护。这里还有一个真实的开发故事：最初的实现是「只要 classpath 上有 MySQL 驱动就自动切换数据库」，而我的开发机恰好跑着 MySQL，结果数据被静默写进了数据库，看起来一切正常。后来先改成必须显式打开数据库，最终干脆收敛为「仅 MySQL 存储」，把文本文件落盘方式与那个开关一并删除，让环境不再有隐式决定行为的机会。代价是部署时必须准备一个可用的 MySQL，这一点在配置模板里写清楚了。

**问题 7：离线消息是怎么实现的？**

答：已经在网络层与服务端实现。服务器路由私聊时，如果接收方不在线，消息仍然落库并保持「未投递」状态，同时给发送方回 OFFLINE 确认；接收方下次登录成功后，服务端查询自己的未投递消息并逐条补投，补投成功后才把记录标记为已送达。幂等由稳定消息标识保证：客户端发出私聊后登记待确认项，5 秒未收到 MSG_ACK 就复用同一个标识重发，服务端按标识判重（命中即回 DUPLICATE，不再转发、不再入库）；客户端另维护已渲染标识的有界集合，补投与重发都不会重复显示。如果接收方收到补投后没来得及确认就断线，消息保持未投递，下次登录会再次补投，也就是「至少一次投递加客户端去重」。界面上的展示细节随后续界面完善继续打磨。

**问题 8：文件传输怎么保证完整性？如果只校验总长度够不够？**

答：不够。总长度一致只能说明字节数对得上，不能说明内容没被改过或没有块被替换。本项目的做法是：发送前对源文件做一次流式 SHA-256 并把结果随 FILE_REQUEST 与 FILE_END 一起发出；接收方写完最后一块后再对本地文件做一次流式 SHA-256，两者比对。同时接收端严格校验块序号连续性，发现乱序或重复立即中止。长度校验只是必要条件，散列校验才是充分条件。另外校验失败时一定会删除残缺文件，避免留下一个「看起来正常但内容损坏」的文件。

**问题 9：你的发送者字段可以被伪造吗？**

答：不可以。客户端确实可以在消息里填任意 sender，但服务器在处理任何业务之前，会从当前连接取出已登录用户名，强制覆盖消息的 sender 字段。也就是说身份的唯一来源是连接的登录状态，而不是消息内容。同理，未登录的连接除了注册与登录之外的消息一律被拒绝。接收方看到的发送者一定是真实的登录身份。

**问题 10：口令为什么用 PBKDF2，而不是 MD5 或单轮 SHA-256？**

答：MD5 有两点不合适：一是抗碰撞性已被攻破，二是它的设计目标是快速摘要，不是抗暴力破解；单轮加盐 SHA-256 虽然挡住了彩虹表，但单张显卡每秒仍可尝试上亿次，挡不住逐账号爆破。本项目改用 PBKDF2WithHmacSHA256，迭代 12 万次、派生 256 位，存储格式为 pbkdf2$120000$hex，把迭代次数写进散列本身，以便将来提高强度时旧散列仍可校验。每个用户有独立的随机 16 字节盐，校验使用常量时间比较，避免比较耗时泄露前缀匹配程度。升级前写入的单轮加盐 SHA-256 仍然可以登录，登录成功后会被透明重算为 PBKDF2 格式，用户无需改密。需要说明的是，工业界更推荐 bcrypt 或 Argon2 这类专门的慢散列，本题受「不引入第三方依赖」约束，选择了 JDK 标准库内的 PBKDF2。

**问题 11：Swing 界面为什么不卡？网络线程怎么和界面通信？**

答：Swing 是单线程模型，所有组件操作都必须发生在事件分发线程 EDT 上，如果在网络线程里直接改组件，轻则界面异常，重则随机崩溃或死锁。本项目的做法是在界面基类 BaseUI 里提供两个方法：onEdt 用于投递更新任务，runOnEdtAndWait 用于需要等待结果的场景；所有子界面更新组件只能走这两个方法，ClientUI 是唯一的消息分发者，网络回调只做协议解码。这里有一个真实的教训：改造界面的过程中，文件传输窗口是在网络接收线程里创建的，而日志文本是在 EDT 上追加的，两个线程分别持有 AWT 树锁和文档锁并互相等待，界面直接卡死。我是用界面线程无响应时打印的线程转储定位到这对反向持锁的，修复办法是把窗口创建、显示与文本追加作为一个整体投递到 EDT。登录、服务器发现这类耗时操作使用 SwingWorker 放到后台线程执行，完成后在 done 回调里更新界面，所以连接过程界面不会假死。

**问题 12：服务器能同时处理多少连接？线程池满了会怎样？**

答：连接数上限由配置项 server.max.connections 控制，默认 200。线程模型采用「一个连接一个线程」：每个 ClientHandler 的整个生命周期都阻塞在对象流读取上，属于典型 IO 密集型任务，因此连接线程池用 ThreadPoolExecutor(0, maxConnections, 60s, SynchronousQueue) 按需创建、空闲回收，而不是固定大小线程池——固定线程池会让超出线程数的连接永久排队，表现为服务器已接受连接却毫无响应（这个坑我在压测中真实踩到并修复，见缺陷 D-09）。如果连接规模继续增长，正确做法不是无限加线程，而是改成 NIO 加事件循环，把线程数压到与 CPU 核数同数量级。

**问题 13：聊天记录为什么改用 MySQL 存？**

答：因为查询与约束都变得直接：按用户与日期范围查询、关键字检索、导出取数都走 SQL 与索引，不必再解析文件；message_id 上的唯一索引天然服务于幂等去重，delivered 列天然服务于离线补投，chat_file_log 还能按结果统计成功率。隐私方面，content 列写入前经 AES-GCM 加密，直接用数据库客户端查看只有 Base64 密文；加密口令由 security.message.secret 提供，缺失时服务器拒绝启动。代价是需要一个可用的 MySQL 实例，并且 db.url 的 serverTimezone 必须填数据库真实时区，否则命令行直接查库时时间会整体偏移。历史上基于文本文件的按天分文件方案已经整体删除。

**问题 14：如果客户端在文件传输中途断线，会发生什么？**

答：分两种角色。如果接收方断线，发送方在写下一块时会收到 IO 异常，文件发送线程终止，关闭发送侧的 RandomAccessFile 资源，并通过界面提示传输失败。如果发送方断线，接收方会在一段时间内收不到后续块，服务器的连接超时扫描（60 秒无活跃）会把该连接清理掉，接收方一侧需要用户取消或超时中止，中止时删除残缺文件并清理资源。当前的不足是：没有主动的传输超时检测，也就是说发送方断线后接收方依赖用户操作或连接清理来结束任务，这一点可以作为改进项——给文件传输单独增加块级超时。

**问题 15：客户端收到的消息会不会重复显示？发送方自己发的消息是从哪来的？**

答：不会重复。本项目约定的策略是：服务器广播群聊消息时，发送方也会收到服务器回传的副本，但发送方界面在本地已经直接追加了自己发送的内容；因此客户端的显示策略需要按消息来源去重。私聊同理，发送方界面直接本地回显，接收方才从网络接收。这也是用户列表、群聊窗口过滤条件里要判断消息类型和对端的原因，这部分逻辑被抽象在聊天面板基类的 accepts 方法中，私聊与群聊各自实现自己的过滤规则。

**问题 16：单例 ChatServer 为什么会有「提前初始化」的问题？你怎么修？**

答：这是真实遇到的缺陷。最初 ChatServer 把业务服务（用户服务、消息服务）作为字段在声明处直接初始化，而 Java 的字段初始化发生在构造阶段——也就是 getInstance 第一次被调用时。如果此时配置文件还没被读取，服务就会用默认的数据目录把路径固化下来，之后即使配置生效也不再改变，表现为「改了配置文件但不生效」。修复方式是把业务服务的创建延迟到 start 方法里，保证配置在使用前已经加载完成。这个缺陷的教训是：单例的初始化时机和配置加载时机之间存在耦合，凡是涉及外部配置的资源，都应该延迟到明确的启动阶段创建。

**问题 17：如果老师让你现在新增一种消息类型，需要改哪些文件？**

答：三步。第一步，在 MessageType 枚举里增加一个类型并给出中文描述。第二步，如果新消息需要新的字段，就继承 Message 增加子类并实现 getSummary；如果只是复用现有字段，直接使用已有的 TextMessage 或 SystemMessage 即可，用 ChatMessageFactory 创建。第三步，在客户端与服务端的处理分支里各增加一个钩子实现，服务端在 AbstractMessageHandler 的子类中处理，客户端在 handleIncoming 的分派逻辑中处理。整个改动不会影响其他模块，因为类型是枚举、创建走工厂、分派走统一入口。这也正是这套设计的目的。

**问题 18：你的测试为什么不用 JUnit？47 个用例怎么跑起来的？**

答：题目约束是纯 Java SE 标准库、不引入第三方依赖，所以我自己写了一个极简框架：定义一个 Test 注解用于存放中文用例说明，TestRunner 通过反射扫描测试类的公共无参实例方法，读取注解输出用例名，调用方法并根据是否抛出异常判定通过或失败，最后汇总通过与失败数量，失败时以非零退出码结束，方便用退出码在连续执行中判断结果。框架还提供了断言方法与临时目录辅助。这样做还有一个额外收益：注解加反射这个机制，我是在自己实现测试运行器的过程中真正搞明白的。
