## 一、先建立三句话的全局图景

1. **一个服务器进程 + 任意多个客户端进程**。服务器监听 TCP 9527，客户端连上来；服务器另外监听 UDP 30000，用来回答"谁在局域网里"。
2. **服务器是中枢**：收消息、校验、转发、落库；客户端负责发消息、收消息、画界面。聊天记录只存 MySQL，文件内容只在中继链路上流动、不落服务器磁盘。
3. **一条消息在网络上是 Java 对象**（`Message` 子类），通过 `ObjectOutputStream` / `ObjectInputStream` 传输；落库前正文用 AES-GCM 加密。所以"协议"就是"消息类的字段 + 消息类型枚举"。

把这三句话记住，后面所有类都能挂到这张图上。

## 三、分层地图：每个包到底管什么

```
com.chat
├── common      公共契约：消息体系、用户、常量、配置、编解码、工厂、反序列化过滤器
├── exception   自定义异常：ChatException / UserNotFoundException / FileTransferException
├── util        无状态工具：口令散列、消息加解密、导出渲染、文件与日期
├── dao         数据访问：泛型接口 + JDBC 实现
├── service     业务规则：用户、消息、文件、文件日志、AI 小助手
├── server      服务器：主服务、连接处理、消息分派、在线表、UDP 发现、控制台
└── client      客户端：网络层 + Swing 界面（ui、ui.theme）
```

### 3.1 common：全项目共享的"语言"

| 类 | 职责 | 为什么在这里 |
|---|---|---|
| `Message` | 抽象基类：id、messageId、type、sender、receiver、timestamp；抽象方法 `getSummary()` | 客户端与服务器共用同一套消息定义，避免两端各写一份协议 |
| `TextMessage` | 文本消息，额外带引用三字段 | 私聊、群聊、控制报文都复用它 |
| `FileMessage` | 文件消息：传输编号、文件名、大小、分块数、校验和、进度 | 文件协议的所有元信息都在这里 |
| `SystemMessage` | 系统通知 | 上线、下线、错误提示 |
| `MessageType` | 35 种消息类型枚举 | 分派依据 |
| `ChatMessageFactory` | 工厂：创建各类消息、校验正文、生成系统消息 | 把"构造合法消息"收口到一处 |
| `MessageFilter` | 反序列化过滤器：白名单 + 深度 + 数组 + 每条消息独立字节/引用预算 | 安全边界，见 4.9 |
| `Config` | 读 `config/chat.properties`，支持系统属性覆盖 | 配置只加载一次 |
| `Constants` | 端口、超时、上限、用户名规则、角色、AI 常量 | 禁止硬编码 |
| `User` | 用户实体，`clearCredential()` 脱敏 | 跨层传递 |
| `Result<T>` | 统一返回结果：成功/失败/数据/消息 | 泛型落地 |
| `UserListCodec` | 在线用户列表编码为文本 | 复用文本消息通道 |
| `FileTransferCodec` | 文件请求编码为文本 | 兼容旧客户端 |
| `AvatarCodec` | 头像 PNG 校验（文件头 + 尺寸 + 像素上限） | 服务端不解码整图 |
| `JsonCodec` | 严格 JSON 解析（深度、转义、数字语法） | AI 响应解析 |

### 3.2 exception：异常体系

- `ChatException`：业务与持久化异常的基类。
- `UserNotFoundException`：删除不存在的用户。
- `FileTransferException`：文件传输失败（不存在、超限、校验和不符、分块错序）。

用处：DAO 抛出受检的 `ChatException`，Service 转成 `Result.fail(...)`，界面只展示中文原因，不把堆栈丢给用户。

### 3.3 util：工具层

| 类 | 关键点 |
|---|---|
| `SecurityUtil` | PBKDF2WithHmacSHA256，12 万次迭代，16 字节随机盐；兼容历史单轮 SHA-256，登录成功后透明升级；常量时间比较 |
| `MessageCipher` | AES/GCM/NoPadding，12 字节随机 IV，128 位 tag；密钥由 `security.message.secret` 经 PBKDF2 派生；密文前缀 `enc:v1:` |
| `MessageExporter` | 把消息渲染成可读文本；`contentOf` 负责解密与占位替换 |
| `FileUtil` | 文件名清洗、重名避让、分块数、SHA-256、人类可读大小 |
| `DateUtil` | 统一日期时间格式与解析 |

### 3.4 dao：数据访问层

```
BaseDao<T, ID>          泛型接口：save / update / delete / find / findAll
UserDao extends BaseDao 用户专属：findByUsername / count / ...
MessageDao extends ...  消息专属：分页、未投递、标记已投递、撤回、搜索
JdbcUserDao             手写 JDBC 实现，构造时 CREATE TABLE IF NOT EXISTS
JdbcMessageDao          手写 JDBC 实现，所有 SQL 集中在这里
JdbcFileLogDao          文件传输审计表
```

要点：

- 没有 ORM，全部 `PreparedStatement` 参数化，杜绝 SQL 注入。
- `JdbcUserDao` 运行期会补 `avatar` 列，并校正列注释，保证老库能直接升级。
- `chat_message` 的 `message_id` 有唯一索引，是服务端幂等去重的最后一道防线。

## 四、代码怎么跑起来：十条主链路

这一节是全文核心。每条链路都按"谁调用谁 → 关键校验 → 结果"写，照着方法名就能在代码里找到。

### 4.1 服务器启动

入口：`ChatServer.main` → `SwingUtilities.invokeLater(new ServerUI(server))`。
真正的启动在用户点"启动服务"后调用 `ChatServer.start()`：

```
start()
├─ 检查 Config.messageSecret() 非空           // 为空直接拒绝启动，避免弱密钥落库
├─ initServices()                             // new UserService / MessageService / FileLogService
├─ 检查数据库可用性                            // 不可用拒绝启动，不存在降级存储
├─ userService.initAdminIfAbsent()             // 仅当 admin 不存在且配置了口令
├─ registerAiAssistant()                       // 配置齐全才注册虚拟成员 ai
├─ new ServerSocket(port)                      // 绑定 9527
├─ ThreadPoolExecutor(0, maxConnections, SynchronousQueue)  // 按需创建、空闲回收
├─ 启动 chat-accept 线程 → acceptLoop()
├─ 启动 DiscoveryResponder                    // UDP 30000
└─ 心跳扫描 scheduleWithFixedDelay(scanIdleConnections, 20s)
```

`acceptLoop()` 每接受一个连接，就 `new ClientHandler(socket, this, maxFileSize, heartbeatTimeout)` 丢进线程池。线程池核心数为 0、队列为 `SynchronousQueue`，所以不会出现"连接被接受但线程都在忙、请求无限排队"的假死。

答辩可以主动讲：**为什么不用固定大小线程池**——每个连接线程会阻塞在 `readObject` 上，固定池一旦占满，后来的连接永远排队，表现是"服务器接受了连接却毫无响应"。

### 4.2 客户端连接与登录

```
ChatClientApp.main
└─ LoginUI
   ├─ 发现服务器：DiscoveryClient.discover()（可手动填 IP）
   ├─ 连接：ChatClient.openConnection(host, port)
   │  ├─ openSocket：Socket → ObjectOutputStream(flush) → ObjectInputStream
   │  │              → MessageFilter.forClientInput() → 启动 chat-receiver 线程
   │  └─ startWorkers：发送池(2)、ACK 扫描、心跳
   └─ 登录：ChatClient.login(name, password)
      └─ 发 LOGIN，正文 "用户名|密码"
```

服务端：

```
ClientHandler.run
└─ dispatch → handleSystemMessage → handleLogin
   ├─ splitFields(content)                    // 字段数与字符集校验
   ├─ UserService.login(name, password, clientAddress())
   │  ├─ 锁定检查（同一"用户名+来源"失败 5 次锁 5 分钟）
   │  ├─ 查库、SecurityUtil.verifyPassword
   │  ├─ 历史 SHA-256 → 成功后透明升级为 PBKDF2
   │  └─ 写 last_login_time
   ├─ UserManager.register(user, this)         // 同一账号不允许重复登录
   ├─ sendLoginResult("1|原因|用户名|昵称|角色")
   ├─ onUserOnline：广播系统通知 + 广播用户列表
   ├─ sendSessionResumeResult(token)           // 30 分钟有效的会话令牌
   └─ pushOfflineMessages()                    // 最多 200 条
```

客户端收到 `LOGIN_RESULT` 后由 `LoginUI` 打开 `ClientUI`，`ClientUI` 注册为 `ChatListener`，之后所有服务器消息都进 `ClientUI.onMessage`。

**这一段的答辩点**：连接与登录拆成两步，是为了注册、改密码时不需要"先登录"；登录成功才注册进在线表，避免幽灵用户。

### 4.3 私聊：一条文本消息的完整一生

发送端：

```
PrivateChatPanel 发送
└─ BaseChatPanel.sendCurrentInput()
   └─ PrivateChatPanel.doSend(content)
      └─ ChatClient.sendPrivateTextReturningId(receiver, content, quoteId, quoteSummary)
         ├─ buildText：new TextMessage，type=TEXT_PRIVATE，生成 messageId(UUID)，填引用
         ├─ sendTrackedId：放入 pendingMessages（等 ACK，超时会重发）
         └─ send → writeObject + flush + reset
```

服务端：

```
ClientHandler.run
└─ dispatch → handleTextMessage
   ├─ requireLogin()                           // 未登录直接拒绝
   ├─ instanceof TextMessage                   // 防止用别的子类伪装文本
   ├─ ChatMessageFactory.checkTextContent      // 长度 ≤ 2000、字符集、非空
   ├─ text.setSender(username)                 // 强制覆盖发送者，防伪造
   ├─ sanitizeQuote(text)                      // 引用必须能在库里查到且本人可见，否则清空
   ├─ 若 receiver == ai → handOffToAiAssistant
   ├─ ensureMessageId + existsByMessageId      // 幂等：重复消息直接回 DUPLICATE
   ├─ UserManager.sendTo(receiver, outgoing)   // 在线则写入对方连接
   ├─ MessageService.saveMessage(outgoing)     // 无论对方是否在线都落库（离线补投依据）
   ├─ 回 MSG_ACK：DELIVERED / OFFLINE / FAILED
   └─ 回显一条摘要给发送方，界面显示"已发送"
```

接收端：

```
ChatClient.receiveLoop
└─ readObject → handleIncoming
   ├─ HEARTBEAT_ACK / MSG_ACK / SESSION_RESUME 先处理并 return
   ├─ OFFLINE_MESSAGE：先回 ACK，再判重
   ├─ acceptIncoming：按 messageId 去重（只对聊天内容）
   └─ notifyMessage → ClientUI.onMessage
      └─ onEdt：切到事件分发线程
         └─ PrivateChatUI/PrivateChatPanel.onMessage → MessageBubble
```

**关键设计**：

- `messageId` 是跨端稳定标识，`id` 只是本地序号，落库后还会被数据库自增主键覆盖，所以不能用 `id` 去重。
- "先转发、再落库、最后 ACK"的顺序是有意的：ACK 代表"服务器已经负责"，只有转发与落库都成功才回 DELIVERED；落库失败即使已转发也回 FAILED，让客户端重试。
- 接收方离线时也落库（`delivered=0`），这是下次登录补投的唯一依据。

### 4.4 群聊

发送端 `ChatClient.sendGroupText` → `TEXT_GROUP`，`receiver=""`。

服务端 `handleTextMessage` 判断 `type == TEXT_GROUP`：

```
outgoing.setReceiver("")
UserManager.broadcastText(outgoing)   // 遍历所有在线连接 send
MessageService.saveMessage(outgoing)  // 广播消息也落库
```

客户端收到 `TEXT_GROUP` → `ClientUI.onMessage` → `GroupChatPanel.onMessage`；窗口没打开时只累计未读，不弹窗。

用户上线/下线时，`UserManager.broadcastSystem` 发 `SYSTEM`，`broadcastUserList` 发 `USER_LIST`，群聊窗口会看到"用户 xxx 上线了"。

### 4.5 文件传输：请求、同意、分块、校验

这是全项目最绕的一条链路，答辩时按"五帧"讲最清楚。

```
① FILE_REQUEST   发送方 → 服务器 → 接收方
② FILE_ACCEPT    接收方 → 服务器 → 发送方
③ FILE_CHUNK * N 发送方 → 服务器 → 接收方
④ FILE_END       发送方 → 服务器 → 接收方
⑤ FILE_RESULT    接收方 → 服务器 → 发送方
```

具体代码：

**发送方发起**：

```
FileTransferUI 选择文件
└─ ChatClient.sendFile(receiver, file)
   ├─ FileService.prepareSend：检查存在/大小 ≤ 200MB/可读，算总块数与 SHA-256
   ├─ pendingSends.put(transferId, request)
   ├─ FileTransferCodec.encode(request) 包成 TextMessage
   └─ 把类型改成 FILE_REQUEST 后发送
```

请求用文本消息承载，是为了让旧客户端至少能识别"这是一条消息"而不是直接反序列化失败；后续帧直接是 `FileMessage`。

**服务端登记**：

```
handleFileMessage
├─ 校验 message.sender == 登录用户名
├─ decodeFileRequest：文本 → FileMessage
├─ 拒绝 ai（"小助手只支持文字问答"）
├─ 校验 transferId 长度、接收者格式
└─ switch：
   FILE_REQUEST → handleFileRequest
      ├─ 文件大小 ≤ maxFileSize
      ├─ 接收方必须在线
      ├─ TRANSFER_REGISTRY.putIfAbsent(transferId, session)  // 防编号被覆盖劫持
      └─ relay 给接收方
   FILE_ACCEPT → acceptTransfer：只有登记过的接收方能同意
   FILE_CHUNK/END → relayTransferStep：必须是登记的发送方、已同意、未结束
   FILE_RESULT/REJECT → finishTransfer：参与者校验 → relay → 落库
```

**接收方接收**：

```
ClientUI.onMessage(FILE_REQUEST)
└─ FileTransferUI 弹窗（同意/拒绝）
   └─ ChatClient.respondFileRequest(accepted=true)
      ├─ FileService.openReceive：在 data/received 创建目标文件（重名自动加 (1)）
      └─ 发 FILE_ACCEPT
```

之后 `ChatClient` 收到 `FILE_CHUNK` → `FileService.appendChunk` 写盘并校验序号；收到 `FILE_END` → `FileService.finishReceive` 校验 SHA-256；成功/失败都发 `FILE_RESULT`。

**服务端收尾**：`saveTransferRecord` 往 `chat_message` 写一条文件记录（文件名、大小、校验和、结果），往 `chat_file_log` 写审计行。**文件内容不落库，服务器只中继。**

**答辩点**：

- 为什么 64KB 一块：内存占用与文件大小无关；TCP 上单帧过大容易造成长时间阻塞与超时。
- 为什么有 SHA-256：分块、中继、落盘任何一步出错都能在最后发现，不会"看起来传完了但文件坏了"。
- 为什么要有 `TRANSFER_REGISTRY`：否则任何人可以伪造 `transferId` 把别人的传输接收者改到自己名下，截获文件。
- 为什么没有断点续传：课程范围外；当前失败会清理残缺文件，重传即可。

### 4.6 历史查询、搜索、导出

**历史查询**（私聊窗口打开时自动拉最新一页，向上翻页）：

```
ChatClient.requestHistory(target, from, to, peer, cursor, limit)
└─ HISTORY_REQUEST 正文：target|from|to|peer|cursor|limit
   （target 字段被服务端忽略，查询对象恒为登录用户名）
```

服务端 `handleHistoryRequest`：

```
MessageService.queryPage(username, peer, from, to, beforeId, limit)
├─ SQL 条件：sender/receiver 涉及本人 + 可选 peer + 时间范围 + id < cursor
├─ ORDER BY id DESC LIMIT n
└─ 每条记录解密正文（失败显示占位）
响应正文：
  1|<条数>|<peer>|v2
  #beforeId=<本页最小主键>
  时间|发送者|接收者|messageId|内容
  ...
```

`v2` 是行格式版本，因为正文本身可能含竖线，不能靠"数段数"猜格式；`#beforeId` 恒定占一行，客户端解析位置固定。

**搜索**：`SEARCH_REQUEST` → `MessageService.search(requester, keyword)`。因为正文是密文，SQL 的 `LIKE` 匹配不到，所以先查本人可见记录、在应用层解密后匹配。结果条数有上限，避免一次解密全库。

**导出**：

```
BaseChatPanel 工具条"导出"
└─ ChatClient.requestExport(scope)   // scope = "" 全部 / @ALL 群聊 / @用户名 私聊
   └─ EXPORT_REQUEST
服务端：
   queryHistory(username, null, null)   // 只查本人可见
   filterExportScope(rows, scope)       // 在已查回的数据上筛，不另写一条 SQL
   MessageExporter.render(rows, address)
   → EXPORT_RESULT 正文："1|条数\n<渲染文本>"
客户端：
   原生保存对话框选路径 → 写文件
```

**答辩点**：可见性规则只在数据层写一次（`queryHistory` 的 SQL），导出在上层筛，不重复拼条件；如果上层再写一份 `AND`，抄错一份就是越权。

### 4.7 消息撤回

```
气泡右键"撤回"（仅本人、2 分钟内可点）
└─ ChatClient.requestRecall(messageId)
   └─ MSG_RECALL 正文 = messageId
服务端 handleRecallRequest：
├─ MessageService.recall(messageId, requester)
│  ├─ 按 messageId 查记录
│  ├─ sender 必须是 requester
│  ├─ 时间必须在 2 分钟内
│  ├─ UPDATE recalled=1, content=占位文本
│  └─ 重复撤回幂等
├─ 回执 MSG_RECALL：OK|messageId 或 FAIL|messageId|原因
└─ notifyRecallPeer：
   ├─ 私聊 → 通知对端
   ├─ 群聊 → 广播给除发起者外的全体在线用户
   └─ 自己给自己 → 跳过
```

撤回后三条路径同时看不到原文：历史查询、关键字搜索、导出都走 `MessageExporter.contentOf` / `recall` 逻辑，读到占位文本 `[该消息已撤回]`。

**答辩点**：为什么群聊撤回要广播——群聊是全员广播，只回发起者的话，其他人会一直看着一条服务端已经不存在的消息；为什么用库里的记录决定通知谁——请求正文可伪造，不能拿它当收件人。

### 4.8 心跳、断线重连、离线补投

**心跳**：

- 客户端每 15 秒发 `HEARTBEAT`；服务器回 `HEARTBEAT_ACK`。
- 服务器每 20 秒扫描一次，60 秒没有任何消息的连接判定掉线，关闭并广播下线。
- 任何消息都会刷新 `lastActiveTime`，不是只靠心跳。

**重连**：

```
receiveLoop 读失败 → handleConnectionLost
├─ 用户主动退出 → 直接结束
└─ 否则启动 chat-reconnect 线程
   └─ reconnectLoop：指数退避 → openSocket → resumeSession
      └─ SESSION_RESUME 带令牌 → 服务端 touchSessionToken
         ├─ 有效：恢复登录态，续期 30 分钟
         └─ 过期：回失败，客户端提示重新登录
```

令牌只存在内存，不写日志、不落盘。

**离线补投**：

```
发送方 → 服务端发现接收方离线
├─ 消息仍落库（delivered=0）
├─ 回 ACK OFFLINE
接收方下次登录
├─ pushOfflineMessages：查 delivered=0，最多 200 条
├─ 逐条发 OFFLINE_MESSAGE
├─ 客户端先回 MSG_ACK，再去重渲染
└─ 服务端 markDelivered
```

这是"至少一次投递 + 客户端按 messageId 去重"，不是"恰好一次"。TCP 写入成功只代表数据进了对方操作系统缓冲区，进程崩溃仍会丢，所以要 ACK + 落库 + 补投。

### 4.9 反序列化安全

`ObjectInputStream` 的反序列化可以构造 gadget 链，必须在读之前设过滤器：

- `MessageFilter.forServerInput()`：白名单 `com.chat.common.*;java.lang.*;java.time.*;java.util.*;!*`，深度 8，数组 65536，每条消息 1MiB / 20 万引用。
- `MessageFilter.forClientInput()`：同样的白名单，每条消息 64MiB / 800 万引用。
- 每条消息读取前调用 `beginMessage()` 重置预算基线。

**为什么客户端预算大**：导出结果是一整条消息，可能很大；如果客户端也用 1MiB，导出稍大的记录就会把连接打断。

**为什么必须按条重置**：如果预算按整条连接累计，长会话聊到一定条数就会被误杀。这正是项目早期真实踩过的坑（D-22/D-23），`ProtocolTest` 里有两条用例专门固定这个行为。

### 4.10 局域网自动发现

```
DiscoveryClient.discover()
├─ 向 255.255.255.255:30000 和本网段广播地址发 "LANCHAT_DISCOVER"
├─ 另发一次 127.0.0.1 回环探测（单机演示也能发现）
└─ 收集 "LANCHAT_ANNOUNCE|ip|port|在线人数"
```

服务器 `DiscoveryResponder` 收到请求后回自己的 `localAddress()`、端口、`UserManager.size()`。

失败不影响核心功能：客户端可以手动填 IP。部分无线 AP 开了客户端隔离会屏蔽广播，这是网络环境问题，不是程序缺陷。

### 4.11 AI 小助手（可选加分）

```
配置 ai.bot.id + ai.api.token 都非空
└─ ChatServer.registerAiAssistant()
   └─ UserManager.registerVirtualUser(ai)   // 不占连接、不计入在线人数
用户私聊 ai
└─ ClientHandler.handleTextMessage → handOffToAiAssistant
   └─ AiAssistantService.ask(asker, question, sink)
      ├─ allowAsk：同一提问者 3 秒一次
      ├─ 线程池异步 HTTP POST
      ├─ 响应体上限 1MiB（流式读取，超限立即中止）
      ├─ JsonCodec 严格解析
      └─ deliverAiReply → 以 ai 身份回一条私聊
```

细节：

- 令牌只放请求头，异常信息会 `redact()`，不写日志。
- 接口地址必须是 http/https 且有主机名，否则视为未配置。
- AI 对话不落库；打开会话窗口拉历史只会得到空页。
- 给 ai 发文件直接拒绝，不触发外部请求。

### 5.4 容易加分的"技术难点"讲法

评委常问"你遇到什么难点"。下面四个都是真实存在于代码里的，讲的时候要带"现象 → 根因 → 方案 → 验证"：

1. **对象流死锁**：两端都先 `new ObjectInputStream` 会互相等头部。解决：先建 `ObjectOutputStream` 并 `flush()`，再建输入流。位置：`ClientHandler.initStreams`、`ChatClient.openSocket`。
2. **长会话被反序列化过滤器误杀**：早期把 `maxbytes/maxrefs` 当整条连接累计，聊到几十条就断。解决：`MessageFilter.beginMessage()` 每条重置，服务端 1MiB、客户端 64MiB。验证：`ProtocolTest` 两条用例 + 集成 IT-09 150 条。
3. **引用伪造**：客户端可自填"引用了某人说的话"。解决：服务端按 `quoteId` 查库、校验可见性、用真实正文重建摘要，查不到就清空引用而不是照单全收。位置：`ClientHandler.sanitizeQuote`。
4. **群聊撤回只通知发起者**：其他人界面还留着已撤回的消息。解决：群聊撤回广播给除发起者外的全体在线用户。位置：`notifyRecallPeer`。验证：IT-10。

## 七、高频追问与回答

**Q1：为什么不用 Netty / Spring？**
课程明确禁止第三方框架；而且这个规模用 JDK 原生 `ServerSocket` + 线程池足够，能把网络编程的细节讲清楚。唯一的外部 jar 是 MySQL 驱动。

**Q2：为什么用 Java 原生序列化，不用 JSON？**
原生序列化让消息类直接成为协议，开发快、类型安全；代价是跨语言差、有反序列化风险。项目用白名单过滤器 + 每条消息预算补上了安全边界。如果重做，会选"长度前缀 + JSON/Protobuf"。

**Q3：消息怎么保证不丢？**
发送方生成 `messageId` 并放入待确认表；服务端按 `messageId` 幂等去重、落库；接收方回 `MSG_ACK`；未确认的消息超时重发；接收方离线时 `delivered=0`，下次登录补投；客户端按 `messageId` 去重。语义是"至少一次"，不是"恰好一次"。

**Q4：并发怎么做？**
在线表用 `ConcurrentHashMap`；每个连接发送加 `sendLock`；监听器与观察者用 `CopyOnWriteArrayList`；服务器连接用可伸缩线程池；客户端网络回调统一切到 EDT 再碰 Swing。共享可变状态尽量收口到一两个类。

**Q5：数据库表怎么设计的？**
`chat_user` 以用户名为 PK，存盐与散列、角色、头像；`chat_message` 用自增 id 做分页，`message_id` 唯一索引做幂等，`delivered` 做补投，`recalled` 做撤回，按 receiver/time/sender 建索引；`chat_file_log` 单独记传输审计。

**Q6：密码怎么存？**
PBKDF2WithHmacSHA256，12 万次迭代，每个用户 16 字节随机盐，存 `pbkdf2$120000$hex`；校验用常量时间比较。历史单轮 SHA-256 在登录成功后透明升级。数据库里没有明文。

**Q7：聊天记录加密的密钥从哪来？**
`security.message.secret` 经 PBKDF2 派生 256 位密钥；每条消息随机 12 字节 IV；密文前缀 `enc:v1:`。口令变更后旧密文无法解密，这是设计取舍，文档里写明了。

**Q8：文件传输为什么服务器不存？**
课程要求是"发送文件"，不是"文件服务器"；服务器只做中继，接收方落盘并校验，既省磁盘又避免服务器成为单点存储。代价是双方必须在线。

**Q9：头像为什么只校验文件头？**
完整解码 4096×4096 的 PNG 可能瞬间吃几百 MB 内存，构成解压炸弹。服务端只读 PNG 签名、IHDR 尺寸与 IDAT 存在性，限制 256×256 像素与 32KB，客户端负责缩放裁切。真正渲染在客户端做。

**Q10：断线重连怎么做的？**
客户端读失败后进入重连线程，指数退避重建 Socket，用 30 分钟有效的会话令牌发 `SESSION_RESUME`；服务端校验令牌并续期。令牌只在内存，不写日志不落盘。

**Q11：AI 小助手安全吗？**
令牌只放请求头，异常信息脱敏；接口地址必须是 http/https；响应体 1MiB 上限；同一提问者 3 秒限频；配置不全自动不启用，服务器行为与未接入完全一致；AI 对话不落库。

**Q12：测试为什么不用 JUnit？**
项目没有 Maven/Gradle，引入 JUnit 要手工管多个 jar，换机器容易跑不起来。自研 `@Test` + 反射运行器零依赖，57 条单元 + 10 条集成都是真实断言；测试库隔离、临时目录隔离都做了。

**Q13：项目最大的不足是什么？**
网络层没有 TLS，局域网抓包可见；Java 序列化耦合两端版本；单服务器没有横向扩展；文件不支持断点续传；离线群聊只增不减。这些在 `docs/known-issues.md` 里有记录，不是不知道，而是课程范围内有意取舍。

**Q14：如果让你继续做，下一步做什么？**
协议换成"长度前缀 + JSON/Protobuf"；加 TLS；文件分片落盘与断点续传；消息已读回执做完整；服务器做多实例与消息转发；把界面测试自动化。

## 十、最后：答辩表达的三条建议

1. **先图后码**：每讲一个功能，先画/指架构图上的那条线，再打开对应类。评委跟得上，你也不会乱。
2. **先结论后细节**：例如"文件传输是五帧协议，核心是分块 + 校验"，然后再展开 `FILE_CHUNK` 与 SHA-256。
3. **主动说边界**：网络层不加密、文件不支持离线、消息是至少一次。主动说明取舍，比被问住更可信。
