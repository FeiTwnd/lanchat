## 一、测试目的与范围

### 1.1 测试目的

1. 验证需求文档中 FR-1 至 FR-17 各项功能需求的实现与验收口径一致。
2. 验证零第三方依赖约束下，项目在干净环境可编译、可运行、可自动化验证。
3. 验证网络协议层（TCP 对象流 + UDP 发现）在真实服务器与真实客户端之间的端到端行为，而非被 mock 的逻辑。
4. 验证密码存储、输入校验、路径清洗等安全相关实现的正确性。
5. 采集性能与稳定性基线数据，暴露与需求指标不符之处。

### 1.2 测试范围

覆盖范围：

- `common`：消息模型与工厂、用户模型、用户列表编解码、配置与常量。
- `util`：`SecurityUtil`（盐值与散列）、`FileUtil`（分块、重名、清洗、格式化、校验和）、`DateUtil`。
- `dao`：`JdbcUserDao`、`JdbcMessageDao`、`JdbcFileLogDao`（存储只保留数据库后，这三者是相应 DAO 接口的唯一实现）。
- `service`：`UserService`、`MessageService`、`FileService`。
- `server`：`ChatServer`、`ClientHandler`、`UserManager`、`DiscoveryResponder`、控制台界面。
- `client`：`ChatClient` 网络层、登录与主界面、私聊与群聊面板、文件传输界面。

不覆盖范围（本次明确不做）：

- 图形界面的主观视觉评价（配色是否好看、是否符合个人审美）：走查脚本只能验证"窗口形态、控件类型、交互行为、
  渲染次数"这类可判定的事实，审美与易用性仍需人工评审；走查覆盖项见第十二节。
- 数据库在多机、真实网络与长时间大数据量下的性能表现（本次在单机回环上验证了功能、连接数与 60 秒稳定性，未做长期压测）。
- 真实多机局域网环境（本次在单机回环 127.0.0.1 上执行，跨机与时延特性需另测）。
- 8 小时长稳与 10 万条消息规模的压力指标（仅完成 60 秒稳定性采样与规模说明）。

## 四、测试框架说明

### 4.1 为什么不用 JUnit

题目要求不使用现成的应用框架，且交付环境可能无外网，无法保证 Maven 仓库或 JUnit jar 可用。若为了写测试而引入 JUnit 依赖，
会与"测试框架零依赖、`javac` 编译后即可运行"的交付方式冲突，也会让测试代码与主源码的依赖边界变得模糊。因此项目自研了一个极简测试框架，
仅使用 JDK 自带的反射与注解，功能上覆盖本课程设计所需的全部断言能力。项目唯一的第三方依赖是数据库连接所需的 MySQL Connector/J 驱动，
它与测试框架无关，仅在运行期连接数据库时需要。

### 4.2 框架组成

| 文件 | 行数 | 职责 |
| --- | --- | --- |
| `src/test/java/com/chat/test/Test.java` | 30 | 用例标记注解 `@Test("用例说明")`，`RUNTIME` 保留，仅可用于方法 |
| `src/test/java/com/chat/test/TestRunner.java` | 316 | 反射扫描标注方法并执行，提供断言方法与汇总输出；失败时以非零退出码结束 |
| `src/test/java/com/chat/test/TestDatabase.java` | 182 | 测试数据库助手：把连接地址指向独立测试库 `lanchat_test`，每个用例前清空用户表与消息表；数据库不可用时提供跳过原因 |
| `src/test/java/com/chat/test/JarPackager.java` | 144 | 构建辅助类，用于把字节码打包为可执行 jar（不属于测试用例） |

断言方法一览：`assertTrue`、`assertFalse`、`assertEquals`、`assertNotEquals`、`assertNotNull`、`assertNull`、`assertArrayEquals`。
其中 `assertArrayEquals` 在失败时会报出"长度不一致"或"第 N 字节不一致"，用于文件逐字节比对的精确定位。

### 4.3 设计要点

1. **注解即用例说明**：`@Test` 的 `value` 就是用例名称，测试输出、测试用例表与源码三者文本一致，避免"表里不一"。
2. **方法名字典序执行**：`collectTestMethods` 对方法名排序，保证多次运行的输出顺序稳定，便于逐行比对。
3. **隔离与清理**：`createTempDir` 为需要磁盘产物的用例创建独立临时目录，`deleteRecursively` 在 `finally` 中清理；
   用户与消息数据统一落在独立测试库 `lanchat_test`，由 `TestDatabase.reset()` 在每个用例开始前清空两张表；
   集成测试通过 `lanchat.data.dir` 系统属性把接收文件与导出记录指向临时目录，因此自动化测试既不写入项目 `data/`，
   也不会写进开发者真实使用的数据库。
4. **反射但不吞异常**：捕获 `InvocationTargetException` 后取出 `getTargetException()`，把断言的原始提示打印出来，不隐藏根因。
5. **退出码可编排**：存在失败用例时 `System.exit(1)`，IDE 运行配置或命令行据此判断成败，方便接入后续持续集成。

### 4.5 框架自身的可信度

自研框架存在"用被测代码之外的自制逻辑验证被测代码"的固有风险。为降低风险，采取了三项措施：
一是断言实现极简且集中（`TestRunner` 内 7 个方法，逻辑可一次读完全部）；
二是所有断言失败都会打印期望值与实际值；
三是本次额外使用**仓库外探针**（`/tmp` 下独立编译的 Java 程序）交叉复验关键结论，
包括 IT-06 的竞态判定、并发上限的确认，以及第 1 轮安全加固的攻击者视角验证（见 11.4 节），避免"测试框架自身出错却报告通过"。

1. 口令存储为"随机盐 32 位十六进制 + PBKDF2 散列（`pbkdf2$120000$` 前缀 + 64 位十六进制，共 78 字符）"，相同口令在不同盐下散列不同、相同盐下可复现，
   底层数据中不含明文（UT-SEC-01 至 UT-SEC-03、UT-SVC-05）。
2. 用户列表与注册返回对象均被脱敏，密码散列与盐不随对象外泄（UT-SVC-01、UT-SVC-09）。
3. 登录失败提示统一：账号不存在与密码错误返回完全一致的"用户名或密码错误"（UT-SVC-04），可防止账号枚举。
4. 分块边界正确：0 字节与整块边界均为 1 块，超出 1 字节为 2 块（UT-FILE-02）。
5. 完整性保护有效：块序号错乱抛出异常；SHA-256 不匹配时抛出异常并删除残缺文件，接收目录被清空（UT-FILE-06、UT-FILE-07）。

7. 1MB 随机文件（1MB+123 字节，17 块）传输后逐字节一致，两端 SHA-256 相同（UT-FILE-04）。
8. 用户与消息数据在换用全新 DAO/Service 实例后仍能完整读出（UT-DAO-05、UT-MSG-11），说明数据确实落在数据库中而非进程内存。

```mermaid
sequenceDiagram
    participant T as 测试线程
    participant S as ChatServer
    participant A as alice01 客户端接收线程

    T->>S: bob.close() 触发断开
```

### 9.1 缺陷趋势说明

D-01 至 D-07 全部在"编写自动化测试"这一环节暴露，其中 D-02、D-03、D-04 属于**协议约定不一致**类问题：
两端对同一消息的类型、形态、方向理解不同，且都被吞在各自的异常处理里，界面只表现为"没有反应"。
这类问题仅靠人工点界面极难定位，是引入集成测试最直接的收益。
D-08、D-09、D-10 是本次测试新暴露的问题，说明"测试代码自身也需要被审视"，以及"需求指标必须在真实规模下验证"。
三者已在同一轮内修复并回归：D-08 统一使用连接时注册的缓冲监听器；D-09 把连接处理线程池由固定大小改为按需创建；
D-10 为配置项补齐读取入口。修复后单元 47/47、集成 7/7（连续 5 次），30 客户端并发登录验证通过。

D-12 至 D-14 由答辩前在 IntelliJ IDEA 中实机运行客户端时暴露，暴露路径与前三轮都不同：
D-01 至 D-07 来自自动化集成测试，D-08 至 D-11 来自规模化验收，而 D-12 落在 **GUI 生命周期**上——
`ChatClient` 的对象所有权在"登录窗口"与"主窗口"之间交接，代码用"谁最后 dispose 谁负责关闭"这种隐式约定，
结果登录窗口在交接后仍然把连接关掉。自动化集成测试直接在测试代码里持有 `ChatClient`、不经过窗口生命周期，
因此对该缺陷完全无感知；这说明**界面层与业务层之间的资源所有权必须显式建模**，
也让"界面走查"（第十二节）从"锦上添花"变成了必要的覆盖手段。
D-13 与 D-12 同源，都是"关闭连接会再次回调监听器"这条隐式链路引发的重入问题，
修复方式统一为"先注销监听、再执行关闭"。

D-15 与 D-16 由界面皮肤化改造完成后的 Xvfb 走查暴露，暴露手段是"真实图形环境 + 线程转储"，而非断言失败：
D-15 的表现是"界面不动了"，既没有异常也没有日志，唯一可靠的证据是 `jstack` 式线程转储中两个线程的持锁方向相反；
D-16 的表现是"多了一行"，只能靠对窗口文本做出现次数统计才能发现——人工肉眼很容易当成"我刚才是不是点了两次"。
两个缺陷都落在 **Swing 线程模型**这条容易被忽视的规则上：控件必须在事件分发线程创建与修改，网络回调必须切线程。
D-15 的修复同时简化了结构（面板不再各自监听客户端，改由主窗口统一分发），D-16 随之自然消失，属于"修一个问题顺带消掉一类问题"。

D-17 是"把自己人当成对端"的典型：服务器给出的一条送达回执把发送者与接收者都填成了发送者本人，
客户端的"对端推断"逻辑在这种自收自发形态下退化成了自己，于是凭空多出一个聊天窗口。
值得注意的是，私聊回执在集成测试里是被断言过的正常协议行为（IT-03），单元与集成测试全绿的情况下界面仍然出错——
根因不在协议也不在业务，而在"回执该不该驱动界面"这一层判断缺失，只能靠界面走查发现。
本次修复把"识别回执"放在消息路由的第一道分支，与 D-16 的"唯一分发者"约定一起，构成了界面层的两条硬规则：
同一条消息只渲染一次，且只有真正的会话消息才创建窗口。

D-18 是本轮"精简工程"改造期间用组件级离屏渲染校验发现的，属于**外观与自绘渲染器边界**类问题：
只要渲染器只覆盖单元格的一部分，就必须假定"其余部分可能被外观画上它自己的颜色"，而不能依赖 `UIManager.put`
去改系统外观的配色——GTK 外观直接读自己的主题样式，覆盖键值对它无效。这类问题在系统外观为 Windows LAF 时不会出现，
只在带 GTK 的 Linux 上暴露，因此把 `TreeUI`/`TableUI` 固定为基础外观实现不只是修一个颜色，而是把渲染控制权收回到自绘代码里。
教训同样值得记录：选中态这类"看一眼就知道不对"的观感问题，也可以被写成可判定断言（橙色素像素数必须为 0），
从而进入回归清单，而不是留给下一轮的肉眼复查。

### 10.2 并发上限的修复与验证

修复前的实测明细（缺陷 D-09）：

| 序号 | 结果 | 连接+登录耗时 | 服务器在线人数 |
| --- | --- | --- | --- |
| 第 1 个 | 成功 | 45 ms | 1 |
| 第 2 至第 8 个 | 成功 | 8 至 11 ms | 2 至 8 |
| 第 9 个 | 失败（EOFException） | 79862 ms | 8（不再增长） |

根因：`ClientHandler` 的整个生命周期都阻塞在 `in.readObject()`，属于典型的"一个连接一个线程"模型，
却被提交到 `Executors.newFixedThreadPool(8)`。线程占满后新连接的任务只能排队，
服务器看似接受了连接却永不读取客户端消息，客户端阻塞在对象流头部握手，最终被心跳扫描判超时断开。

修复：连接线程池改为按需创建、空闲回收，并把连接数上限交由配置控制。

| 修复项 | 修复前 | 修复后 |
| --- | --- | --- |
| 线程池类型 | `newFixedThreadPool(8)` | `ThreadPoolExecutor(0, maxConnections, 60s, SynchronousQueue)` |
| 连接数上限 | 常量 `MAX_CONNECTIONS`，实际未生效 | 配置 `server.max.connections`，默认 200，随配置生效 |
| 第 9 个及以后连接 | 永久排队直至超时断开 | 立即分配线程并完成登录 |

修复后的验证结果（30 个真实客户端并发登录）：

| 指标 | 实测值 |
| --- | --- |
| 成功登录客户端数 | 30 / 30 |
| 全部登录总耗时 | 208 ms |
| 单个客户端登录耗时 | 134 至 201 ms |
| 登录后服务器在线人数 | 30 |
| 并发场景下私聊投递 | 成功 |
| 客户端全部断开后在线人数 | 0（清理无残留） |

结论：连接线程模型修复后，并发能力不再受固定线程数限制，上限由 `server.max.connections` 明确控制，
与 NFR-2 的验收口径一致。缺陷 D-09 关闭。

### 10.3 稳定性与长跑观察方法（未执行部分的操作口径）

8 小时长稳观察本次未执行，后续按以下口径补做，避免以短时数据推断长期结论：

1. 以 IDEA 运行配置「服务器（图形控制台）」启动服务器（等价命令 `java -cp out/production/LANChat com.chat.server.ChatServer`），保持 8 个客户端在线，客户端按固定速率互发文本消息。
2. 以 `jcmd <pid> GC.heap_info` 与 `jcmd <pid> Thread.print` 每 30 分钟采样一次堆占用与线程数。
3. 观察 `chat_message` 表行数与磁盘占用的增长量，确认历史写入不导致内存中累积消息对象（服务端统计用 `SELECT COUNT(*) FROM chat_message;`）。
4. 以 `jcmd <pid> GC.class_histogram` 对比首末两次采样，确认 `Message` 与 `ClientHandler` 实例数不随运行时长单调增长。
5. 判定口径：8 小时后堆占用无持续上升趋势、线程数不增长、在线用户表人数与客户端数量一致，即视为通过 NFR-9。

### 10.4 性能数据的解释边界

上述延迟与吞吐数据在**单机回环**上取得，且执行机为 32 逻辑核、15GiB 内存的开发机，
不能直接外推为"千兆局域网真实表现"。局域网真实性能受交换机、无线链路与跨机调度影响，
需在两台以上真实主机上复测才能对 NFR-1 与 NFR-3 给出最终结论。
此外，本次执行期间主源码正被并行重构，数据为特定源码快照下的结果。

`java.awt.Robot` 产生真实的鼠标按下、拖动、释放事件，用 `SwingUtilities` 投递任务后对窗口 `paintAll`
截图，用反射与公开 API 读取控件状态（是否无边框、是否含自定义标题栏、树上有多少在线/离线用户、聊天文本中某句话出现几次）。
