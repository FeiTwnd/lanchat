缺陷 D-23：反序列化过滤器 maxrefs 是连接级累计量，正常聊天到 66 条即掉线
================================================================================

结论
--------------------------------------------------------------------------------
maxrefs 与 maxbytes 一样绑定的是“同一个 ObjectInputStream 上累计的值”，
而且流里的 TC_RESET（对端 out.reset() 写出）会清空句柄表却不清零该计数器。
本项目 ChatClient.writeObject 与 ClientHandler.send 都是“每发一条 reset 一次”，
重置会让类描述符在每条消息里重发一遍，引用消耗随之上升：

    实测（纯文本消息、每条 reset）：约 15.2 个引用/条
    maxrefs=1000  →  读到第 66 条即被判 REJECTED

用户可见症状不是“掉线”三个字，而是客户端重连流程被触发：

    警告: 连接已失效: 接收消息失败: filter status: REJECTED，进入重连流程

重连期间在线用户列表为空（界面提示“没有在线用户，无法发送”）、
气泡索引与撤回菜单随之重建（表现为“撤回功能时而消失”）。
日志把容量问题记成了安全问题，因此此前一直没被怀疑到这里。

三、为什么抬高取值不降低防护
--------------------------------------------------------------------------------
真正抵御“反序列化炸弹”的是 maxdepth 与 maxarray：炸弹的危害在于用小报文膨胀出
巨大的对象图，而这两项卡的正是膨胀本身，且它们每次 readObject 都会重置、
不随连接时长衰减。maxbytes 与 maxrefs 是累计量，攻击者要耗尽它们只能真的把
那么多字节发过来，不构成放大效应。

`testFilterStillBlocksForeignType`（java.io.File 仍被拒）与
`testFilterStillLimitsArrayLength`（65537 字节的数组仍被拒）两条用例把
“白名单与 maxarray 未受影响”固定下来。

改动位置
--------------------------------------------------------------------------------
src/main/java/com/chat/common/ChatMessageFactory.java
  SERIALIZATION_FILTER_PATTERN:
    maxrefs=1000  →  maxrefs=50000000     （D-23）
    maxbytes=4194304  →  maxbytes=1073741824 （D-22，本轮之前已改）

取值依据：本项目最省引用的文本消息约 15 个引用 / 485 字节，
5 千万引用对应约 1 GiB 流量，与 maxbytes 的天花板量级对齐，
因此不会出现“字节数还没到、引用数先耗尽”这种更难排查的假象。

四、后续更正（2026-10-10，第 5 轮审查后追加，保留上文原有记录不改）
================================================================================

上文第三节“为什么抬高取值不降低防护”的结论**已被证伪**，现更正如下：

1. 抬高 maxrefs / maxbytes 并不是“不降低防护”，而是**等于取消了防护**。
   白名单里的 `java.util.*` 不受 maxarray 约束（JDK 21 只对部分集合调用 checkArray），
   而未登录连接在 `requireLogin()` 之前就会 `readObject()`：把报文里 `LinkedList` 的
   元素个数声明成 1500 万，旧阈值 1GiB / 5 千万引用会放行，服务端堆随即被撑到数百 MB 直至 OOM。
   一条消息里每个元素在流上只是一个 5 字节的 TC_REFERENCE，放大倍数接近 8 倍——
   这正是 maxdepth / maxarray 管不到的资源放大路径，因此第三节“真正抵御炸弹的是
   maxdepth 与 maxarray”的说法不成立。

2. 仅抬高取值还有更隐蔽的代价：累计上限被抬高后，临界点只是被推远而不是被消除。
   纯文本约 538 字节 / 15.2 个引用每条，1GiB 先到，约 200 万条文本之后整条连接仍会被判 REJECTED。
   换言之 D-22 / D-23 当时只是把掉线的临界点从“第 66 条”推到了“第 200 万条”，
   根因（把连接级累计量当单条上限用）一直没动。

3. 根治方式：新增 `common.MessageFilter`，在类型白名单之上按“每条消息独立预算”判定——
   读循环在每次 `readObject` 前调用 `beginMessage()` 把基线推到当前累计量，
   之后只看相对基线的增量。服务端读 1 MiB / 20 万引用，客户端读 64 MiB / 800 万引用；
   白名单本身去掉累计的 maxbytes / maxrefs，只保留 maxdepth=8 与 maxarray=65536。
   改动位置：`src/main/java/com/chat/common/MessageFilter.java`（新增）、
   `src/main/java/com/chat/common/ChatMessageFactory.java`（白名单去掉 maxbytes/maxrefs）。

4. 更正后的实测（仓库外探针，原始输出见 `docs/test/evidence/R5-01-反序列化每条消息预算-探针输出.txt`）：
   - 3000 条消息的长会话，累计 1,483,894 字节（单条预算 1MiB）→ 全部通过，不再被累计上限误杀；
   - 65536 字节文件分块（流 66,127 字节）→ 通过；
   - `LinkedList` 声明 100 万个回引用元素（流仅 5,000,047 字节）→ **被拒绝**，
     即 1GiB / 5 千万引用时代能通过的放大攻击，现在被拦住。

5. 回归：单元测试 57/57、集成测试 10/10（仓库默认配置与 ai 留空两种配置下均为 10/10），
   其中集成用例 9（长会话稳定性，150 条不断线）就是为这条链路补的固定证据。
